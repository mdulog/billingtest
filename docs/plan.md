## Phase 0 — Setup + containerization (25–30 min)
- `npm init`, TypeScript, **Kysely** (query layer), **Fastify** (HTTP),
  **Vitest** (tests).
- `Dockerfile` + `docker-compose.yml` + `.dockerignore` (see below).
- Drop `usage_events.json` into the repo once available.
- Commit: `chore: project scaffold`
- Commit: `chore: containerize service and database`

**Everything runs in containers — `docker compose up` is the only setup step.**
This is worth real time rather than being a footnote: the spec grades whether
"instincts extend past the code itself into how you'd operate this," and a
reviewer who has to hand-install Postgres 17 and match a connection string
before seeing anything work has already formed an opinion. Reproducibility on
someone else's machine *is* an operational property.

`Dockerfile` — multi-stage, so the runtime image carries no compiler or dev
dependencies:

```dockerfile
FROM node:24-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:24-slim AS runtime
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node                      # never run as root
CMD ["node", "dist/server.js"]
```

`docker-compose.yml` — `db`, `api`, and one-shot `migrate` / `ingest`
services. Two details that are easy to get wrong:

```yaml
db:
  image: postgres:17-alpine
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U postgres"]
    interval: 2s
    retries: 15
api:
  depends_on:
    db:
      condition: service_healthy   # not service_started
```

`pg_isready` exits 1 while the server is still starting, so a container that
is "up" is not yet a database that accepts connections. Without
`condition: service_healthy` the API and migrations race the database on a
cold start and fail intermittently — the classic version of this bug.

🚨 **The RLS trap containerization exposes.** The `postgres` image's default
user is a **superuser, and superusers bypass RLS entirely** — `FORCE ROW LEVEL
SECURITY` only covers the table *owner*, not a superuser. If the API connects
with the default credentials, every tenant-isolation guarantee from Phase 1 is
silently inert, and the isolation test would still pass for the wrong reason.
So: migrations create a dedicated non-superuser role, and `api` connects as
that role while `migrate` connects as the owner. This is assumption **T4**,
and containerizing is what forces it to be real rather than assumed.

Config comes from environment variables only — no connection strings in the
image, no secrets in `docker-compose.yml` beyond local-only dev values, and
the service fails fast at startup if `DATABASE_URL` is missing.

**Local runtime is Podman, not Docker** (verified: podman 5.8.4, rootless,
SELinux `Enforcing`, `podman-compose` 1.6.0 available via `podman compose`).
The compose file stays vendor-neutral so a reviewer on Docker runs
`docker compose up` and this machine runs `podman compose up` — but three
Fedora/Podman specifics are worth pre-empting:

- **Use a named volume for `pgdata`, not a bind mount.** Under SELinux
  Enforcing, bind mounts need a `:z`/`:Z` relabel suffix or the container gets
  permission denied; under rootless Podman they also pick up UID-mapped
  ownership that confuses Postgres. Named volumes sidestep both.
- **`COPY` the fixture into the image rather than bind-mounting it.** Same
  reasoning — it removes the only other bind mount the ingest step would need.
- **Verify `depends_on: condition: service_healthy` actually gates startup**
  under `podman-compose`, which has historically been the shakiest part of its
  Compose-spec coverage. If it doesn't hold, fall back to a retry loop in the
  migrate entrypoint rather than assuming ordering.

**Note:** the real `usage_events.json` is not in hand yet. A *synthetic*
stand-in lives at `fixtures/usage_events.sample.json`, generated by
`scripts/generate-usage-events.mjs` (a dev tool, not part of the service),
so schema work isn't blocked. The real dataset belongs at the repo root as
`usage_events.json`; re-run ingestion against it when it arrives, since it
will contain edge cases the synthetic fixture doesn't.

**Decided — Kysely over an ORM.** An ORM abstracts away exactly the thing
being graded (schema reasoning); raw `pg` costs an afternoon of hand-rolled
row mapping. Kysely is typed SQL you still write yourself.

**Decided — Fastify over Express.** Its per-route JSON Schema validation makes
"validate `from`/`to` at the boundary and 400 on bad input" declarative rather
than hand-rolled:

```ts
app.get('/customers/:customerId/usage', {
  schema: {
    params: { type: 'object', required: ['customerId'],
      properties: { customerId: { type: 'string' } } },
    querystring: { type: 'object', required: ['from', 'to'],
      properties: {
        from: { type: 'string', format: 'date-time' },
        to:   { type: 'string', format: 'date-time' },
      } },
  },
}, handler);
```

Pair it with `setErrorHandler` inspecting `error.validation` /
`error.validationContext` so validation failures return a structured 400 and
everything else returns a generic message — never a stack trace or raw DB
error to the client.

## Phase 1 — Schema + migrations (35–45 min)
- Look at the actual JSON first — don't design blind. Note which fields are
  per-event vs. per-customer (e.g. `plan`, `user_email` may belong on a
  `customers`/`users` table, not repeated per event).

**One big table vs. several** (write-up Q1 asks this by name, so answer it
explicitly rather than only presenting the chosen design):

A single wide `usage_events` table holding `plan` and `user_email` inline is
genuinely defensible for this workload — it's append-only, the read pattern is
aggregate-over-a-date-range, and no join beats no join. That's why event
warehouses (and the source file itself) look like this.

It's rejected here for three concrete reasons, not on principle:
1. **Update anomalies with real cost.** Per B3 a customer's plan changes over
   time. Denormalized inline, correcting a plan means rewriting every historical
   row for that customer; normalized, it's one interval row.
2. **No integrity boundary for tenancy.** `customer_id` as a bare column has
   nothing enforcing that it names a real customer. The FK plus RLS policy is
   what makes isolation a database property rather than a convention.
3. **Conflicting values become unresolvable.** The fixture already contains
   `"enterprise"` and `"Enterprise "` for one customer. In a wide table there's
   no single row that says which is authoritative — the contradiction is the
   data. A `customers` row makes it a resolvable conflict at ingest time.

The tradeoff accepted in return: every per-plan billing query now pays a range
join. That's mitigated by the GiST index and by keeping `customers.plan`
denormalized for the hot "current plan" read — i.e. the design is *mostly*
normalized with one deliberate exception, not dogmatically either.
- Write migrations: `customers`, `users` (if warranted), `events` (or
  `usage_events`), maybe `endpoints` as a lookup if normalized FKs are
  worth it vs. a plain text column — state the tradeoff, don't resolve it
  perfectly.
- **Decided: multi-tenancy via Postgres RLS (rung 2).** The requirement says
  isolate customers "at the database level" — an app-level `WHERE customer_id`
  is discipline, not isolation. RLS makes a forgotten `WHERE` return zero rows
  instead of another tenant's data (fail-closed):

  ```sql
  ALTER TABLE usage_events ENABLE ROW LEVEL SECURITY;
  ALTER TABLE usage_events FORCE ROW LEVEL SECURITY;
  CREATE POLICY tenant_isolation ON usage_events
    USING (customer_id = current_setting('app.current_customer', true));
  ```

  Per request, inside the transaction: `SET LOCAL app.current_customer = $1`.
  `SET LOCAL` is load-bearing — a plain `SET` leaks tenant context to the next
  borrower of a pooled connection.

  Not doing (name in the write-up, don't build): schema-per-tenant, and
  `PARTITION BY RANGE (occurred_at)` monthly partitions for the "wildly
  different volumes" scaling question.
- Index the columns the endpoints will filter/sort on (`customer_id`,
  `occurred_at`, `endpoint`) — decide now while the query shapes are fresh.
- Commit: `feat: initial schema and migrations`

**Second migration, same phase — plan history.** Owner confirmed upgrades
take effect immediately while downgrades/cancellations wait for period end
(`docs/assumptions.md` B3), so `customers.plan` alone can't answer "which
plan was in effect when this event occurred." Keep this a genuine second
migration rather than folding it into the first — the spec asks how you
evolve a schema, and this is a real instance of that, not a contrived one.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE customer_plans (
  id           bigserial PRIMARY KEY,
  customer_id  text      NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  plan         text      NOT NULL,
  valid_period tstzrange NOT NULL,
  EXCLUDE USING gist (customer_id WITH =, valid_period WITH &&)
);
```

The exclusion constraint makes overlapping plan periods for one customer
impossible to store — not an app-level promise, a database-enforced one.
`customers.plan` stays as a denormalized cache of the current plan
(maintained in the same transaction), which is a direct, nameable answer to
requirement #1's "FK vs. denormalized for read performance."
- Commit: `feat: plan history schema`

## Phase 2 — Ingestion (40–50 min)
- Read JSON, validate/normalize, upsert customers, insert events.
- **Owner decision: the dedupe key.** The source has no `event_id`, so the key
  must be derived. The fork: include `metadata` in the hash (a redelivery with
  a corrected `duration_ms` counts as a distinct billable event) or exclude it
  (same event, deduped). No right answer — pick one and defend it.
  Enforced as `UNIQUE (customer_id, dedupe_key)` + `ON CONFLICT DO NOTHING`,
  which makes re-running the loader idempotent.
- Rejects go to an `ingest_rejects` table with a reason code rather than being
  dropped — the reject-rate-by-reason counter is the operational metric for
  write-up question 3.
- Watch the trap: `login` events legitimately carry no `duration_ms`. "Missing
  duration" and "malformed record" are different things; conflating them
  rejects valid data.
- Wrap the batch insert in a transaction.
- Commit: `feat: usage_events ingestion`

**Plan history derivation, same phase.** Pure function over one customer's
events ordered by `occurred_at`: walk in time order, and on a plan change
apply the monotonic-tier guard from `assumptions.md` S3 — an **upgrade**
(higher tier) closes the current interval and opens a new one; a
**downgrade** is rejected as dirty data, since B2 forbids mid-period
downgrades. Keep it pure (no DB) so it unit-tests directly; the derived
intervals then get inserted into `customer_plans` inside the same ingest
transaction. This is where the exclusion constraint gets exercised for
real, not just at the DDL level.
- Commit: `feat: derive plan history from usage events`

## Phase 3 — HTTP API (45–60 min)
Three endpoints, all scoped by `customer_id` and date range:
- `GET /customers/:id/usage?from=&to=` — summary (event counts, total
  duration_ms), broken down **per plan** via a `LEFT JOIN customer_plans ON
  occurred_at <@ valid_period` — `LEFT`, not inner, so an event landing in a
  coverage gap still counts (surfaces under a `null` plan bucket) instead of
  silently vanishing from a billing report
- `GET /customers/top?from=&to=&limit=` — ranked usage across customers,
  labeled with `customers.plan` (current standing, not historical
  attribution — it's a cross-tenant admin view, not per-period billing)
- `GET /customers/:id/endpoints?from=&to=` — per-endpoint breakdown
- Validate `from`/`to` and `customer_id` at the boundary; return 400 on bad
  input, not a raw DB error.
- Commit: `feat: billing query endpoints`

## Phase 4 — Tests (30–40 min)
- Ingestion: dedupe logic and malformed-record handling — these are the
  parts with actual decisions in them, test those first if time is short.
- Plan history derivation (unit, no DB): single-plan-throughout → one
  unbounded interval; mid-period upgrade → two abutting intervals;
  mid-period downgrade → rejected, one interval; casing/whitespace variants
  → normalized before comparison, one interval.
- The worked example, as an integration test: 100 events under `pro`, an
  upgrade, 200 under `enterprise`, all inside one month. A month-wide
  summary must return two rows (100/`pro`, 200/`enterprise`) — not 300 under
  `enterprise`. This is the test that proves B3 was implemented, not just
  documented.
- At least one endpoint against a real DB (or test container), asserting on
  response shape and values, not just status 200.
- Commit: `test: ingestion and endpoint coverage`

## Operational posture (material for write-up Q3)

Decide this while building, not while writing — the instrumentation has to
exist in Phase 2/3 code for the write-up to be honest.

**Measure** (per `assumptions.md` A6): events ingested per run, reject count
by reason code, dedupe hit rate, ingest wall-clock duration, endpoint p95
latency. Structured logs with named fields (`{CustomerId}`, `{RejectReason}`,
`{EventCount}`) — never interpolated strings, never the raw event payload,
which contains user emails.

**The distinction that matters:** page on things that are *silently wrong and
cost money or leak data*. Do not page on things the design already absorbs.
The `ingest_rejects` table is a pressure valve, not an alarm — a non-zero
reject count is the system working as intended. It becomes an alarm when the
*rate changes*, because that means the upstream contract moved.

| Signal | Response |
|---|---|
| No successful ingest run in > N hours | 🚨 **Page.** Billing data is silently going stale; every hour compounds the gap. |
| Reject rate jumps well above its trailing baseline | 🚨 **Page.** Implies an upstream schema change — events are being dropped and usage under-billed, with no user-visible symptom. |
| Query returns rows for a tenant other than the session's | 🚨 **Page.** RLS makes this impossible by construction, so it firing means the policy was dropped or the app connected as a superuser. Security incident. |
| API 5xx rate or pool exhaustion | 🚨 **Page.** Ordinary availability. |
| Individual malformed records | 🎫 Ticket. Expected; that's what the quarantine table is for. |
| New unrecognized `event_type` (per I9) | 🎫 Ticket. Product shipped a feature; accepted by design, worth a look. |
| Events arriving after subscription lapse (per B6) | ⚠️ Depends on B6 — grace period is a metric, access-revocation failure is a page. **Open question**, so it's currently instrumented but not alarmed. |
| Slow query on the heaviest customer | 🎫 Ticket. Known consequence of D8's skew; the partitioning answer, not a 2am problem. |
