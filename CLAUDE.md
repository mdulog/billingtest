This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A take-home exercise (`docs/spec/takehome_requirements.md` — **read-only, `chmod 444`, never edit it**): a multi-tenant usage/billing service in Node.js/TypeScript backed by Postgres, ingesting `usage_events.json` and exposing HTTP endpoints for billing-relevant queries.

**Read `docs/plan.md` and `docs/assumptions.md` before making any design decision.** This is not optional context — it's the project's actual source of truth:

- `docs/plan.md` is the phase-by-phase build plan with decisions already made (multi-tenancy mechanism, dedupe strategy, framework choices) and their rationale. Check it before re-deciding something it already settled.
- `docs/assumptions.md` is the assumptions register: every gap the spec left open, tagged by provenance (📄 spec-derived / 🗣️ owner-supplied / 🔍 inferred / ⚠️ invented) with the cost of being wrong. Assumptions tagged ⚠️ invented are the ones most likely to need revisiting; owner-supplied ones (🗣️) are settled and shouldn't be re-litigated without asking.
- `docs/adr/` holds MADR-format Architecture Decision Records for the settled decisions (RLS for tenant isolation, plan history as a range table, Fastify/Kysely, containerization, the derived dedupe key, the non-superuser role) — read the relevant ADR before touching code that implements one of these, rather than re-deriving the reasoning from the code alone.

Both documents are living records — when a design decision changes, update the relevant entry rather than letting the docs drift from the code.

### Containers

**This machine runs rootless Podman on SELinux Enforcing, not Docker** — use `podman compose`, not `docker compose` (the compose file itself is vendor-neutral; either works on a machine that has it). Verified: podman 5.8.4, `podman-compose` 1.6.0.

```bash
podman compose up -d --build   # db + api; the only setup step for a clean checkout
podman compose down
podman compose logs -f api
```

`docker-compose.yml` defines `db`, `migrate`, `ingest`, and `api` — `migrate` and `ingest` are one-shot services (`service_completed_successfully`), and `api` waits on both.

⚠️ Bind mounts need `:z`/`:Z` SELinux relabeling and fight rootless Podman's UID mapping — this repo uses a named volume (`pgdata`) instead and `COPY`s the fixture into the image. Keep new compose services following that pattern rather than adding bind mounts.

## Architecture

**Multi-tenancy is enforced at the database level via Postgres RLS, not application-level `WHERE` filtering.** The requirement is explicit about "isolate ... at the database level" — see `docs/plan.md` Phase 1. The design:

- `ALTER TABLE ... FORCE ROW LEVEL SECURITY` + a policy on `current_setting('app.current_customer', true)`.
- Per-request: `SET LOCAL app.current_customer = $1` inside the same transaction as the query — `SET LOCAL`, not `SET`, because a pooled connection would otherwise leak tenant context to whoever borrows it next.
- **The API must connect as a dedicated non-superuser role (`app_user`), never the Postgres superuser.** Superusers bypass RLS entirely — `FORCE ROW LEVEL SECURITY` only restricts the table owner, not a superuser — so connecting with default `postgres` credentials would make tenant isolation silently inert while still appearing to pass a same-tenant query test. This role is created in `migrations/001_initial_schema.ts`. `docker-compose.yml`'s `api` service already points `DATABASE_URL` at `app_user`, ahead of that role existing.
- `/customers/top` is the one legitimately cross-tenant query (admin/ops view) and uses a separate, non-RLS-scoped connection: `app_admin` (`LOGIN`, `NOSUPERUSER`, `BYPASSRLS`, `SELECT`-only), created in `migrations/004_admin_role.ts` and wired to the API via `ADMIN_DATABASE_URL` (ADR 0007) — never `app_user`'s RLS-scoped connection, and never customer-facing without revisiting that design choice.

**Plan history is a first-class table, not a column**, because plan changes are asymmetric: upgrades take effect immediately (owner-confirmed), downgrades/cancellations wait for period end. `customer_plans(customer_id, plan, valid_period tstzrange)` with `EXCLUDE USING gist (customer_id WITH =, valid_period WITH &&)` makes overlapping periods for one customer unrepresentable at the DB level, not just disallowed by convention (requires `CREATE EXTENSION btree_gist`). `customers.plan` is kept as a deliberate denormalized cache of the *current* plan for cheap reads — derivable from `customer_plans`, but not sourced from it on every query. See `docs/assumptions.md` B2/B3/B7 and `docs/plan.md` Phase 1/2 for the full reasoning, including the monotonic-tier guard used to distinguish a real mid-period upgrade from dirty/conflicting plan data in the source.

**Ingestion has no natural event ID to dedupe on** — the source schema doesn't include one. The dedupe key is derived excluding `metadata` (ADR 0005) and enforced via `UNIQUE (customer_id, dedupe_key)` + `ON CONFLICT DO UPDATE` on `duration_ms`/`status`/`metadata` — a redelivery with a corrected value overwrites the original rather than being silently discarded, while still making re-running the loader idempotent by construction. Malformed records are quarantined to `ingest_rejects` with a reason code rather than dropped silently — don't conflate "field absent because it's not applicable to this event type" (e.g. `login` events never carry `duration_ms`) with "field malformed"; those get different handling.

**Every RLS-scoped route goes through `withTenant()`** (`src/db/connection.ts`) rather than hand-rolling `SET LOCAL` per handler — it wraps a transaction and issues `select set_config('app.current_customer', $1, true)`, parameterized rather than string-built, since `SET LOCAL` doesn't accept a bind parameter directly. `src/api/errorHandler.ts` maps Fastify validation failures (and the `from >= to` check schema can't express) to 400, and Postgres "not ready yet" codes (`28P01`/`28000`/`57P03`/`3D000`/`ECONNREFUSED` — the migrate/api startup race under `podman-compose`) to 503; it never returns a raw `error.message`, since a DB auth failure's message contains the `app_user` password.

**Config is env-var only and fails fast** (`src/config.ts`) — `DATABASE_URL` missing throws at startup rather than surfacing as a confusing error three layers down later.

**Logging goes through Fastify's injected pino logger, not `console.*`**, everywhere except the top-level startup failure handler in `src/server.ts` (which runs before any logger exists). See `src/db/connection.ts`'s `PoolLogger` interface for the pattern used to keep `src/db/` free of a direct Fastify dependency while still logging at the right severity.

**TypeScript is v7 (the native/Corsa compiler)** — `tsconfig.json` needs an explicit `"types": ["node"]`; TS7 does not auto-include ambient `@types` packages the way earlier versions did. `@types/node` is pinned to the `24.x` line to match the Node 24 LTS runtime target, not whatever major `npm install` resolves by default.
